## NAMAA — Project Status & Technical Verification

Project: NAMAA Smart Agriculture Platform

Purpose of This Document

This document records the implementation status, verification evidence, known limitations, and outstanding tasks of the NAMAA Smart Agriculture Platform.

It distinguishes implemented features from features verified through software tests, live deployment, hardware testing, or expert evaluation. A feature is marked as verified only when supporting evidence is available.
## What NAMAA is
Irrigation decision support for farmers. Sensors (moisture, soil temperature, EC) at several measurement points in a field -> one ESP32 -> Supabase.
A rule-based decision engine decides, from the sensors, the weather, the crop and the soil. RAG + LLM only explain the engine's decision (they never decide).
ML (24 h soil moisture forecast) is PAUSED since 2026-10-23: the engine does not read forecasts and every alert comes from the engine's rules.

## Non-negotiable rules
- No fake data anywhere (no mock numbers in the UI, no placeholder savings). Test fixtures are allowed only inside tests/.
- Missing value = NULL, never 0, never imputed.
- No scientific constant without a source (traceable to `sources`). The engine ignores a soil row that has no `source_id`.
- Fertilization returns `{ "status": "insufficient_data" }` when N/P/K are not measured. Irrigation can still be decided when its inputs exist.
- Weather is per field (latitude / longitude / timezone stored in `fields`), not global.
- ESP32 tokens are stored as hashes. RLS on every table. No secrets in frontend / firmware / git.
- Build step by step. Do not restart the architecture discussion. Do not add tables without a clear justification.

## Stack
React + TypeScript + Vite + Tailwind 3 (`namaa-agritech/`), Supabase (Postgres, RLS, Edge Functions in Deno/TS), Open-Meteo, ESP32 firmware (Arduino C++, in `firmware/`, not yet run on a real ESP32). Python only for ML (paused, `docs/ml/` is empty).
The engine lives in `src/engine/` and is copied into `supabase/functions/_shared/engine/` by `npm run sync-engine` (`npm run check-sync` verifies the copy).

## Database schema (real database as of 2026-10-16, plus the migrations in `supabase/migrations/` up to 2026-10-23)
- `sources(id text, title, source_type, verification_status, created_at, url)`. Rows: `FAO56_TABLE1` (Table 12, status `verified`, see Open decisions), `FAO56_TABLE22` (`unverified`), `FAO56_TABLE19` (`unverified`), `FAO56_TABLE11` (`unverified`), `FAO_FERT_SPECS`, `CDFA_OLIVE_LEAF`, `UCIPM_TOMATO_SOIL` (all `unverified`).
- `crop_coefficients` = FAO-56 Table 12, 134 rows (id uuid, row_id, section, crop, variant, row_type, kc_*_raw/min/max/footnote, max_height_*, crop_name_footnotes, source_ref, source_id).
- `crop_water_params` = FAO-56 Table 22 (maximum root depth Zr and depletion fraction p), created by `20261021090000_crop_water_params.sql`; data file `data/reference/fao56_table22_root_depth_p.csv` (104 lines); `crops.water_params_id` points to it.
- `crops(id, crop_name, created_at, coefficient_id, water_params_id)`: the list the user picks from. `20261021100000_populate_crops.sql` fills it with every crop that has BOTH a Kc row and a Table 22 row (exact name match; nothing guessed).
- `crop_growth_stages` and `crop_irrigation_rules`: exist in the real database (read policy added by `20261021120000_engine_outputs.sql`); they are not created by the migrations of this repo. `20261023100000_growth_stages_table11.sql` adds the columns `plant_period`, `region`, `value_basis`, `source_id` to `crop_growth_stages` and seeds the FAO-56 Table 11 stage lengths of 13 crops (Olives included) (written 2026-10-23; whole table in `data/reference/fao56_table11_stage_lengths.csv`). Any other crop needs its row added by the owner (`docs/ADDING_A_CROP.md`). View `crop_readiness` shows which crops have everything the engine needs.
- `soil_types(id, soil_name, created_at, field_capacity_pct, wilting_point_pct, field_capacity_min_pct, field_capacity_max_pct, wilting_point_min_pct, wilting_point_max_pct, value_basis, source_id)`: the columns after `created_at` and the 9 FAO-56 Table 19 texture classes come from `20261023090000_soil_water_table19.sql` (written 2026-10-23; data file `data/reference/fao56_table19_soil_water.csv`).
- `fields(id, owner_user_id, name, latitude, longitude, timezone, area_m2, created_at, crop_id, soil_type_id)`. `weather_observations(id, field_id, observed_at, air_temperature_c, precipitation_mm, rain_probability_pct, et0_mm, created_at, fetched_at)`: one row per field per hour (unique `field_id, observed_at`).
- `devices(id, field_id, device_name, firmware_version, device_status, last_seen_at, created_at, updated_at)`, `device_tokens(id, device_id, token_hash, created_at, revoked_at)` (hash only, revocable, users cannot read it). Owners can read their own devices (`20261021130000_devices_ingest.sql`).
- `sensor_points(id, field_id, point_name, latitude, longitude, created_at)`: no depth column (one 3-in-1 sensor per point); owners add / rename / remove their own (`20261020120000_owner_manage_sensor_points.sql`).
- `sensor_readings(id, sensor_point_id, measured_at, moisture, soil_temperature, ec, moisture_status, soil_temperature_status, ec_status, created_at)`: values nullable, a status per variable.
- `decisions` (exists in the real database; the engine adds `engine_version`, `irrigation_status`, `details`), `alerts` (kinds `engine`, `forecast`, `savings`; the app reads only `engine` and `savings`), `water_savings`. Owners read their own rows; only the service role writes.
- `ml_model_registry`, `moisture_forecasts`: created but unused while ML is paused.
- `crop_nutrient_sufficiency`, `fertilizers`, `alert_thresholds`: every row needs a `source_id`. `20261023110000_fertilization_reference.sql` fills `fertilizers` (10 FAO products; column `value_basis`) and `crop_nutrient_sufficiency` (Tomato soil P and K; Olives July-leaf N, P, K). `20261023120000_fertilization_doses_soil_notes.sql` (written 2026-10-23) adds the heat limit to `alert_thresholds` (30 C, all crops), the new table `crop_nutrient_rates` (dose ceilings, kg of nutrient per dunum) and the new table `fertilizer_soil_notes` (what a source says about a fertilizer on a soil type or on a condition the app does not record). Details: `data/reference/fertilization_reference.README.md`.
- `nutrient_methods(code, label_en, label_ar, description)`, `nutrient_measurements(id, field_id, nutrient n/p/k, value, unit, method_code, source_kind lab/sensor, measured_at, note, entered_by, created_at)`, `crop_nutrient_sufficiency.method_code` (one limit per crop, nutrient AND method) and `devices.npk_unit` / `devices.npk_method_code`: all from `20261024100000_nutrient_measurements.sql` (written 2026-10-24). RLS: the owner reads the measurements of her fields, can insert LAB results only (not dated more than a day ahead, `entered_by` = herself) and delete her lab results; sensor values are written by the ingest function (service role) and cannot be deleted by the browser.
- `profiles` (name for the greeting, filled by a trigger), `knowledge_chunks` (RAG store, 1536-dimension embeddings).
- Frontend read access: `20261020090000_frontend_read_policies.sql` (owner reads of sensor_points, sensor_readings, decisions, decision_explanations, soil_types). All tables have RLS on; a table with no policy is readable only by the service role.

## Decisions taken for the ingest step (implemented in `sensor-ingest`)
- Moisture is stored as volumetric water content in % (0-100), the same unit as `soil_types` field capacity / wilting point (changed 2026-10-20). A value outside 0-100 is rejected as suspect; no silent conversion.
- Soil temperature in C (-50..100), EC in dS/m (0..100): physical sensor limits (`LIMITS` in `src/engine/ingest.ts`), not agronomic limits.
- Status per variable: `measured` (value present), `not_measured` (sensor sent nothing, value NULL), `suspect` (sent but impossible, value NULL).
- Readings may be older (offline buffering; at most 24 hours old, at most 5 minutes in the future, at most 50 per request).
- NPK values (added 2026-10-24): `nitrogen`, `phosphorus`, `potassium` in a reading are plain numbers >= 0 and <= 1 000 000 (a physical limit of a sensor, not an agronomic one); an impossible or non-numeric one is NOT stored and its sensor is listed in `suspect_nutrient_sensors`. They go to `nutrient_measurements`, not to `sensor_readings`. The unit and the method come from the device settings (`devices.npk_unit`, `devices.npk_method_code`); without them the value is stored as `unspecified` / `sensor_unspecified` and the engine will not judge it. A request that sends no NPK value never reads those settings.
- **Known gap:** duplicates are NOT removed. The database has no unique rule on (sensor point, time) and `sensor-ingest` does not check, so a device that re-sends a reading stores it twice. The engine uses the newest usable reading, so decisions are not affected, but the table grows. (An older version of this file said duplicates were ignored: that was a plan, not the code.)

## Weather function rules (supabase/functions/weather-sync)
- Needs a signed-in user; the user can only sync a field they own (RLS on `fields`).
- Open-Meteo hourly variables: temperature_2m, precipitation, precipitation_probability, et0_fao_evapotranspiration. Units requested explicitly (celsius, mm), time as unix seconds (UTC).
- A missing value stays NULL. A value out of range becomes NULL and is counted. If the response is not as expected, nothing is stored.
- Max one Open-Meteo call per field every 10 minutes. Writes use the service role only.
- Open-Meteo free use is non-commercial: check its licence page before any commercial use.

## Open decisions / unverified
- `sources.verification_status` for FAO56_TABLE1 is `verified` (set by another assistant): the import was checked (134 rows, sums, md5), but keep the status only after the owner has checked the numbers of her crops against the book. `FAO56_TABLE22`, `FAO56_TABLE19`, `FAO56_TABLE11`, `FAO_FERT_SPECS`, `CDFA_OLIVE_LEAF` and `UCIPM_TOMATO_SOIL` are `unverified`.
- Blank Kc ini cell -> group row of the same section, flagged approximate (FAO-56 Chapter 6 text). Mid and end are never inherited.
- Ranges (e.g. tomato Kc end 0.70-0.90) are returned as ranges. Footnotes are returned for review (tomato Kc mid: footnote 2).
- Soil: Table 19 gives ranges (e.g. Loam field capacity 0.20-0.30). The midpoint is a NAMAA choice and the range is wide, so the depletion in mm is uncertain. A value measured on the field (saturate the soil, read the sensor after about 48 h) would be more exact. The web page prints the lower field capacity of Silty clay as "0-30"; it was read as 0.30: check it in the printed book.
- Stage lengths: Table 11 has several rows per crop. The rows seeded are chosen by a NAMAA rule (only Mediterranean row, lengths add up to the printed total, annual crop, no ambiguous variant). Egg plant (printed total 40, lengths add up to 140) and Green gram (lengths add up to 100, printed total 110) disagree with their own printed total on the web page: check the book, then add the rows yourself. The table calls its values a general guide: a farmer's own observation of the stages is better.
- Weather is stored hourly; daily ET0 = sum of the hourly values of the local day (F-002, implemented). Validate against the two-pot experiment.
- Doses are a CEILING taken from the source (California rates per acre converted to kg per dunum, 1 dunum = 1000 m2), never a target; only Tomato P and K and Olives N and K have one (no olive phosphorus: the guideline says P fertilization will not normally improve olive yield; no tomato N: no soil N limit). Soil notes exist only where a source says something (urea and ammonium sulphate by texture and pH, potassium sulphate on light soils); every other fertilizer shows "no soil-type information stored", which is NOT "suitable". Soil pH, salinity and drainage are not recorded in the app. The heat limit of 30 C comes from garden and lawn guidance.
- Fertilization limits are California values (processing tomato soil test; California olive July leaf analysis), not Palestinian. The unit and the method are part of each limit. Potassium chloride (MOP) is not stored on purpose (chloride toxicity risk, the engine does not know the soil). The heat limit (`fertilizer_hold_air_temp_max_c`) has no sourced number: leave `alert_thresholds` empty until the owner finds one. The options are ordered by nutrient content, not by what suits the crop; the soil notes are shown beside them, the farmer chooses.
